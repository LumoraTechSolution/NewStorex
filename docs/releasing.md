# Shipping a new version to shops (M5-11)

The till can update itself. **It does not do so yet**, and this document is both the procedure and
the list of what is missing.

---

## What the channel does, and the one thing it will never do

A running till asks a feed URL twice a trading day, downloads a newer installer quietly in the
background, and **applies it when the shop closes StoreX**. That is the only moment an update is
ever installed.

There is no "Restart now" button, in the screen or in the bridge between the screen and Node. On a
till, that button is a way to stop Postgres under an open shift, lose an unprinted receipt and
leave a cashier holding a queue. The rule that governs the printer, the outbox and the backups
governs this too: nothing that is not the sale may interrupt the sale.

The cashier sees one line — _"Update ready. It will be installed the next time StoreX is closed."_
— and has nothing to do about it. It exists so a shopkeeper who opens on Tuesday to a changed screen
read on Monday that it was coming.

---

## Why it is currently off

`updater.cjs` refuses to run unless **all** of these hold:

| Condition                | Why                                                                     |
| ------------------------ | ----------------------------------------------------------------------- |
| A packaged build         | A developer's `electron .` must never update itself                     |
| `LUMORA_UPDATE_URL` set  | No feed, nothing to ask                                                 |
| That URL is **https**    | Over http the door does not even need a key                             |
| The build is code-signed | Without a publisher name, "update" means "run whatever that URL served" |

The last one is the one that matters and the one that is not met. An update channel is, by
construction, remote code execution on every shop PC that has the product. The only thing between
it and whoever can answer for that URL is the Authenticode check `electron-updater` performs on the
downloaded installer — and that check exists only when there is a publisher name to compare
against. **An unsigned channel is not "an update channel with a SmartScreen warning". It is an open
door.**

So the till logs its reason at startup and does nothing:

```
updater: off — this build is not code-signed, so a downloaded update cannot be verified…
```

`LUMORA_UPDATE_ALLOW_UNSIGNED=1` overrides it for testing the mechanics against a local feed. It is
named to be hard to reach for by accident, and it logs `ENABLED WITHOUT SIGNATURE VERIFICATION` on
every launch. Never on a shop's machine.

## Turning it on

Three things are needed, and none of them are code.

### 1. A code-signing certificate

An OV certificate from a CA (DigiCert, Sectigo, SSL.com). Roughly **$200–400 a year**, and it
requires proving the company exists — allow a week or two. An EV certificate costs more, ships on a
hardware token, and additionally clears SmartScreen immediately rather than after a reputation
period.

Then, in `apps/terminal/package.json` under `build.win`:

```json
"certificateFile": "path/to/cert.pfx",
"certificatePassword": "${env.WINDOWS_CERT_PASSWORD}",
"publisherName": "<the certificate's exact subject name>"
```

`publisherName` must match the certificate's subject **exactly**; that string is what every till
compares a downloaded update against, and a mismatch means every shop silently stops updating.

### 2. Somewhere to serve the feed

Any static HTTPS host — Cloudflare R2 with a public bucket, S3, a plain nginx. It serves two files
per release:

```
StoreX-Setup-<version>.exe
latest.yml
```

`latest.yml` is generated by electron-builder; it carries the version, the file name and a SHA-512
that the till checks before it stages anything.

### 3. The build environment

```bash
LUMORA_UPDATE_URL=https://<your feed host>/win
```

Set at build time — electron-builder interpolates it into the packaged `app-update.yml` — and on the
till, where the runtime reads it. Two places on purpose: a build can be pointed at a staging feed
without rebuilding, and a till can be moved between channels without reinstalling.

## Cutting a release, once it is on

1. Bump `version` in `apps/terminal/package.json`. The installer's name and the feed both come from
   it, and **a release that does not raise the version is a release no till will take.**
2. `pnpm --filter @lumora/terminal dist` with `LUMORA_UPDATE_URL` set.
3. Upload `StoreX-Setup-<version>.exe` **and** `latest.yml` from `apps/terminal/dist/`. Upload the
   installer first: a `latest.yml` that names a file which is not there yet makes every till in the
   country retry a 404 for as long as the gap lasts.
4. Watch one till. `%LOCALAPPDATA%\StoreX\logs\electron.log` says what it decided, in the same
   words either way.

**A till updates on the next quit, not on the next check.** A shop that leaves the PC on for a week
gets it the following Monday. That is the correct trade and it means a release is not a moment — it
is a week.

---

## What has not been done

- No certificate, so **the channel has never run**. The decision logic is tested; the download and
  swap are `electron-updater`'s and have not been exercised against a real feed here.
- No rollback. A bad release is fixed by publishing a higher version, because a downgrade is not
  something the generic provider does — which is one more reason step 4 above watches a single till
  before the rest of the estate ever asks.
- Nothing tells the cloud which version a shop is on. When there are enough shops to care, that
  belongs on the entitlement pull (M4-09), which already runs a conversation in that direction.
